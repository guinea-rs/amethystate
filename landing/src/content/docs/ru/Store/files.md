Пути к файлам данных, метаданных и восстановления можно получить у store.
Имена зависят от движка; не собирайте их вручную:

<!-- shown: asking a store where its files are -->
```rust
match StoreBackend::files_layout(&store) {
    Some(StoreLayout::Single { data }) => {
        println!("everything is in {}", data.display());
    }
    Some(StoreLayout::Sidecars {
        data,
        meta,
        data_backup,
        meta_backup,
    }) => {
        println!("values:      {}", data.display());
        println!("bookkeeping: {}", meta.display());
        println!(
            "kept while rewriting: {}, {}",
            data_backup.display(),
            meta_backup.display(),
        );
    }
    Some(StoreLayout::InMemory) => println!("nothing is on disk"),
    Some(_) => println!("a layout this code does not know yet"),
    None => println!("this engine does not say"),
}
```
<!-- /shown -->

Перечисление описывает файловую структуру движка. Выберите вариант через
`match`, чтобы получить нужный путь. Путь возвращается даже для файла,
которого сейчас нет, например временной резервной копии.

## redb и SQLite: один файл

Оба движка держат значения и метаданные схемы в базе. Отдельного файла
amethystate `.meta` у них нет.

## Текстовые движки: два файла, и ещё два во время записи

| файл | назначение |
| --- | --- |
| `settings.json` | сохранённые значения |
| `settings.json.meta` | версии схем, описания полей и состояние миграции |
| `settings.json.bak` | копия данных при перезаписи во время открытия |
| `settings.json.meta.bak` | копия метаданных на то же время |

Документ с данными читается отдельно, но метаданные нужны store для истории
схемы. Включайте оба файла в собственные резервные копии.

Суффиксы добавляются к **полному имени файла**. Поэтому `settings.user.meta`
не пересекается с `settings.system.meta`, а копии данных и метаданных
не перезаписывают друг друга.

До версии 0.23 метаданные хранились под именем вроде `settings.meta`.
Если нового `settings.json.meta` нет, открытие прочитает старый файл и запишет
новый. Старый остаётся на месте: его может использовать другой store.

## Зачем нужен бэкап

`.bak` — временная защита при открытии, не пользовательский бэкап. Store
сначала читает файлы и выполняет миграции в памяти. Перед перезаписью
изменённого файла он создаёт копию для восстановления; после успешной записи
удаляет её. Неизменённые файлы не копируются и не перезаписываются.

Оставшийся `.bak` поэтому может указывать на прерванное открытие.
Пример создаёт такое состояние:

<!-- shown: a previous open that never finished -->
```rust
std::fs::write(&backup, &good).unwrap();
std::fs::write(&data, "{ this never finished").unwrap();
```
<!-- /shown -->

Файл данных недописан, но копия читается. При следующем открытии store
восстановит данные из неё и запишет предупреждение под таргетом `amethystate`.
Сначала нечитаемый файл сохранится как `settings.json.unreadable`.
После успешной записи восстановленных данных копия удаляется.

Копия создаётся **после успешного чтения**, непосредственно перед перезаписью.
Если скопировать нечитаемый файл поверх целого бэкапа, восстановление станет
невозможным. Ошибка миграции не создаёт новых копий и не перезаписывает
исходные файлы.

Неизменённые файлы не трогают, чтобы открытие одного store не заменило свежие
записи другого устаревшей копией.

## Начать заново

Удаление файла данных начинает новый store, только если рядом нет его `.bak`.
Оставшийся `.meta` тогда не восстанавливает старое состояние: используются
текущие версии схем, а структуры получают defaults при создании.

## Чего копия не обещает

Решение о восстановлении зависит от разбора документа, а не от его полноты
или свежести:

- Обрезанный документ может оставаться синтаксически правильным. Store
  не отличит пропавшие ключи от тех, которые никогда не записывались.
- Если документ разбирается, он принимается как есть, а временная копия может
  быть удалена без восстановления.
- У копии нет надёжного номера поколения. Она может оказаться старее ожидаемого;
  время изменения файла не является достоверной версией.

Считайте оставшийся `.bak` артефактом восстановления, а не точкой отката.
Для важных данных делайте отдельные резервные копии приложения.

SQLite и redb используют протоколы коммита базы, а не этот механизм текстовых
файлов: SQLite — журнал упреждающей записи, redb — новые страницы и двухфазное
обновление заголовка. Они не показывают частично зафиксированные пачки.
