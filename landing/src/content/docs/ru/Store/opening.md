Создайте `Store` через `StoreBuilder`, выбрав расположение файла и движок
хранения. Передавайте его структурам состояния или обращайтесь к данным
напрямую по пути. Клонирование `Store` создаёт ещё один хендл на тот же
открытый store, а не новое соединение с базой или новый файл.

Обычно store остаётся открытым до завершения приложения. Можно также открыть
несколько store с разными файлами или движками.

## По пути, который вы назвали

<!-- shown: opening a store at a path you name -->
```rust
let store = StoreBuilder::new(settings).build()?;
```
<!-- /shown -->

`build` возвращает `Store`, который можно передать в `new_with`. При удалении
store пытается сохранить накопленные записи, но не может вернуть ошибку
вызывающему коду. Если результат нужно обработать, используйте явное
[закрытие](#закрытие).

## Или один раз, на весь процесс

Если не хотите передавать store через всё приложение, установите глобальный.
Он доступен из любой части процесса:

<!-- shown: opening the process-wide store -->
```rust
let _ame = "./app.redb".init_global();

let state = NetworkState::new();
```
<!-- /shown -->

`NetworkState::new()` использует установленный глобальный store вместо
параметра. У структур с `open = manual` такого конструктора нет: store
нужно передать явно — см. [Собственное открытие](/amethystate/ru/state/opening-structs/).
К самому store тоже можно обратиться:

<!-- shown: reaching the global store from anywhere -->
```rust
let store = global_store();
store.kv().set("theme", &"dark".to_string())?;
```
<!-- /shown -->

**Храните guard из `init_global`.** Его удаление закрывает глобальный store.
Поэтому отдельный вызов `"./app.redb".init_global();` сразу закрывает только что
открытый store. Привяжите guard в `main`, например `let _ame = ...`.

Установка второго глобального store при открытом первом вызывает панику.
После закрытия или shutdown можно установить новый. Старые хендлы по-прежнему
относятся к закрытому store; прежний guard не может закрыть замену.
Обращение к глобальному store до установки тоже вызывает панику.

Для обрабатываемых ошибок открытия, например конфига, который UI может
предложить сбросить, используйте возвращающий ошибку `build_global`:

<!-- shown: opening the process-wide store without a panic -->
```rust
let _ame = match StoreBuilder::new("./app.redb").build_global() {
    Ok(guard) => guard,
    Err(InitGlobal::Open(why)) => {
        eprintln!("settings are unavailable: {why}");
        return Ok(());
    }
    Err(InitGlobal::AlreadyInstalled) => unreachable!("opened once, in main"),
};
```
<!-- /shown -->

У билдера есть глобальные варианты: `build_global`, `migrate_global`
и оба после `or_in_memory()`. Они отклоняют установку, если store уже открыт.
Открытый отдельно store устанавливается через `install_global`; если место
занято, метод возвращает неустановленный store.

Миграция и глобальная установка вместе:

<!-- shown: opening it with the migration pass -->
```rust
let (_ame, report) = StoreBuilder::new("./app.redb").migrate_global()?;

if report.has_drift() {
    eprintln!("a struct changed without a version bump");
}
```
<!-- /shown -->

## Пусть платформа скажет, где

Явный путь подходит тестам и инструментам, работающим с выбранным файлом.
Для установленного приложения определите каталог через `located`:

<!-- shown: letting the platform say where the file goes -->
```rust
let config = StoreBuilder::located(|at| at.app("my-app", "settings"))?;

let named = StoreBuilder::located(|at| at.app_under(Layout::App, "my-app", "settings"))?;

let portable = StoreBuilder::located(|at| at.beside_the_executable("settings"))?;
```
<!-- /shown -->

Доступные варианты расположения:

| метод | расположение |
| --- | --- |
| `at.app("my-app", "settings")` | Каталог настроек приложения по `Layout::App`. |
| `at.app_under(Layout::App, ..)` | Каталог по явно выбранной раскладке. |
| `at.beside_the_executable("settings")` | Рядом с исполняемым файлом, для переносимой установки. |

### Какому соглашению следует `app`

`Layout` выбирает правила каталога:

| раскладка | правила |
| --- | --- |
| `Layout::App` | XDG-подобная раскладка на всех платформах, включая Windows и macOS. |
| `Layout::Native` | Нативные каталоги приложений текущей платформы. |
| `Layout::ProjectDirs` | Раскладка крейта `directories`. |

`app` выбирает `Layout::App`, а не `Layout::Native`. Укажите `Native` явно,
если нужны нативные каталоги. `ProjectDirs` позволяет совпасть с существующим
приложением, использующим `directories`.

**После выпуска сохраняйте выбранную раскладку.** Смена правил может перенести
поиск в другой каталог и создать видимость потери настроек.
Зафиксируйте выбор через `app_under`.

### Как переехать, если store уже лежит в другом месте

`located` вызывает замыкание один раз и использует возвращённый `PathBuf`.
До возврата замыкание может найти или перенести существующие файлы.

Переносите всю раскладку движка, не только исходный путь: текстовый store
также имеет метаданные и может иметь файлы восстановления. Например:

<!-- shown: moving every file a store is made of -->
```rust
fn relocate(from: &StoreLayout, to: &StoreLayout) -> std::io::Result<()> {
    for (old, new) in from.names().iter().zip(to.names()) {
        if old.exists() {
            std::fs::rename(old, new)?;
        }
    }

    Ok(())
}
```
<!-- /shown -->

`names` перечисляет все возможные пути раскладки, включая временные файлы,
которых сейчас может не быть. При переносе пропускайте отсутствующие.
Две раскладки одного движка перечисляют соответствующие роли в одном порядке;
`present` оставляет только существующие файлы.

`at.files_at` вычисляет раскладку без открытия старого store:

<!-- shown: a store found where an older release left it -->
```rust
let store = StoreBuilder::located(|at| {
    let now = at.app(&app, "settings")?;
    let was = at.files_at(at.app(&app, "settings-legacy")?, backend);

    relocate(&was, &at.files_at(&now, backend)).ok();

    Ok(now)
})?
.backend(backend)
.build()?;
```
<!-- /shown -->

Приложение решает, как переносить данные: копировать файлы, переименовывать,
спросить пользователя или оставить прежнее расположение. Библиотеке нужен
только итоговый путь. Операция должна допускать повтор, если предыдущий запуск
мог оборваться посередине.

`beside_the_executable` предназначен для доступной на запись переносимой
установки. `Program Files`, `/usr/bin` и подписанный пакет macOS не подходят
для записи настроек и могут вызвать ошибку открытия.

## Каким файлом становится имя

К пути без расширения добавляется расширение выбранного движка:

<!-- shown: letting the engine name the file -->
```rust
let store = StoreBuilder::new(config_dir.join("settings"))
    .backend(Backend::Json)
    .build()?;
```
<!-- /shown -->

Получается `settings.json`. Явное расширение сохраняется:

<!-- shown: naming the file yourself -->
```rust
let store = StoreBuilder::new(config_dir.join("settings.conf"))
    .backend(Backend::Json)
    .build()?;
```
<!-- /shown -->

Получается `settings.conf` с JSON внутри. Формат выбирает `backend`,
не расширение. Если после пути без расширения изменить движок, автоматически
подобранное расширение тоже изменится.

Движки и форматы перечислены в [Установке](/amethystate/ru/getting-started/installation/).

## Что делать, если значение не читается или ключ исчез

Для ошибки чтения и удалённого ключа есть отдельные политики. По умолчанию
нечитаемое значение не даёт создать структуру, а после удаления ключа
открытое поле сохраняет прежнее значение. Чтобы изменить defaults:

```rust
use amethystate::store::OnUnreadable;

let store = StoreBuilder::new(path)
    .rules(|r| r.on_unreadable(OnUnreadable::UseDefault))
    .build()?;
```

Политики задаются на store, структуре или поле. Более конкретное объявление
приоритетнее: поле, затем структура, затем store. Поэтому `UseDefault`
на store не заменяет явный `Refuse` структуры.

Например, восстанавливаемые настройки миниатюр могут использовать defaults
после ошибки, а лицензия должна оставаться читаемой:

<!-- shown: one process, two answers about the same store -->
```rust
#[amethystate(prefix = "thumbnails")]
pub struct Thumbnails {
    #[amestate(default = 0u32)]
    pub generated: u32,
}

#[amethystate(prefix = "licence", on_unreadable = Refuse)]
pub struct Licence {
    #[amestate(default = "".to_string())]
    pub holder: String,
}
```
<!-- /shown -->

При `UseDefault` на store нечитаемый счётчик миниатюр получает default.
Нечитаемая `Licence` всё равно не создаётся, поскольку явно требует `Refuse`.
Наследование политик и живые обновления разобраны в
[Нечитаемых значениях](/amethystate/ru/state/unreadable-values/).

## Что делать, когда не читается сам файл

Нечитаемый файл — не то же самое, что одно нечитаемое значение в правильном
документе. Политики также различаются при открытии и последующем сохранении.

### На открытии

По умолчанию неверная база или неразбираемый документ вызывают ошибку
открытия, а файлы остаются нетронутыми:

```rust
use amethystate::store::WillNotOpen;

let cache = StoreBuilder::new(path)
    .when_it_will_not_open(WillNotOpen::StartFresh)
    .build()?;
```

`StartFresh` удаляет файлы раскладки, включая копии восстановления,
и создаёт пустой store. До удаления записывается предупреждение,
но операция необратима. Используйте её только для восстанавливаемых данных,
например кэша.

Она не отменяет ошибки прав, занятый другим процессом файл, базу SQLite
с меткой другого приложения или базу, требующую более новой SQLite.
Это не основания удалять чужие данные.

### Или работать в памяти

Включите `memory` и добавьте `or_in_memory()` перед `build` или `migrate`,
чтобы при ошибке открытия продолжить с новым store в памяти:

<!-- shown: running in memory when the file will not open -->
```rust
let (store, persistence) = StoreBuilder::new(path).or_in_memory().build();

if let Persistence::InMemory { because } = &persistence {
    eprintln!("settings will not be saved this run: {because}");
}
```
<!-- /shown -->

Результат сообщает, доступно ли сохранение и почему понадобился fallback.
Store в памяти начинает пустым, инициализирует структуры defaults и не
перезаписывает файлы, которые не удалось открыть. Ошибка компоненты миграции
от этого не превращается в успешную миграцию.

`Persistence::OnDisk` означает обычное файловое хранение. Глобальные методы
`build_global` и `migrate_global` поддерживают такой же fallback, но всё ещё
отклоняют уже установленный store.

Для заведомо временной сессии используйте `StoreBuilder::in_memory()` или
`.backend(Backend::Memory)` напрямую. Движок в памяти хранит по значению
MessagePack на путь и не воспроизводит раскладку текстового документа.

### На сохранении

Текстовый файл может временно стать некорректным во время редактирования.
При сохранении нужно решить, что делать с таким документом:

<!-- shown: what a save does with a file that will not read -->
```rust
let store = StoreBuilder::new(path)
    .backend(
        Text::json()
            .when_it_will_not_read(WhenItWillNotRead::TryAgainFor(Duration::from_secs(30))),
    )
    .build()?;
```
<!-- /shown -->

| политика | поведение |
| --- | --- |
| `TryAgainFor(срок)` | Повторять, не меняя файл; после срока перейти к `SetAside`. |
| `SetAside` | Переместить файл в `<имя>.unreadable`, затем сохранить. |
| `Refuse` | Не сохранять, пока файл не читается. |
| `Overwrite` | Заменить документом store, удалив прежнее содержимое. |

По умолчанию используется `TryAgainFor(Duration::from_secs(5))`.
Срок считается от первой попытки, встретившей нечитаемый файл, а не от каждого
повтора. Успешный разбор сбрасывает его. До сохранения записи остаются в памяти.

Для редактируемых пользователем настроек выберите `Refuse` или default,
чтобы защитить незавершённую правку. `Overwrite` допустим, только если старое
содержимое можно отбросить. `SetAside` сохраняет нечитаемый файл отдельно,
но следующая такая копия заменяет предыдущую. У символической ссылки
перемещается целевой файл, сама ссылка остаётся.

Отказ сохранения — ошибка сброса: `save_now` возвращает её, drop записывает
в лог. Эти политики относятся к текстовым документам, не базам redb или SQLite.

## Какие миграции выполняются

- `build` открывает store без выполнения шагов. Регистрация схемы и проверка
  дрейфа при этом работают.
- `migrate` выполняет зарегистрированные шаги и возвращает отчёт. Ошибка
  компоненты не даёт открыть store: `OpenStore::Migrating` содержит отчёт.

После `.migrations()` доступны только методы открытия с миграцией.
Перед открытием можно добавить `or_in_memory()`, а для глобального store
использовать `build_global` или `migrate_global`.
См. [Миграции](/amethystate/ru/migrations/overview/).

## Сброс буфера на диск

Drop пытается сбросить буфер, но может лишь записать ошибку в лог.
Если результат нужен коду, вызовите `save_now`, пока store открыт:

<!-- shown: writing the buffer out and hearing whether it landed -->
```rust
store.kv().set("port", &8080u16)?;

if let Err(report) = store.save_now() {
    eprintln!("settings were not saved: {report:?}");
}
```
<!-- /shown -->

`save_now` возвращает результат сброса и оставляет store открытым.
После ошибки можно повторить попытку, пока буфер доступен. Последующий
Drop тоже попробует сохранить данные и запишет возможную ошибку в лог.

## Закрытие

`close` сбрасывает записи, останавливает фоновую работу и освобождает ресурсы.
В отличие от `save_now`, после него store нельзя использовать для дальнейших
операций хранения:

<!-- shown: closing the store and letting go of the file -->
```rust
if let Err(report) = store.close() {
    eprintln!("the last writes were not saved: {report:?}");
}
```
<!-- /shown -->

Все клоны относятся к тому же закрытому store. Прямые чтения, записи,
перечисления и сбросы возвращают `Closed` своего типа операции. Повторное
закрытие допустимо, но не повторяет сохранение.

`get` поля продолжает возвращать значение из памяти; `try_get` сообщает
`Reason::Closed`, чтобы обозначить кэшированное состояние.

Закройте store перед передачей файла другому процессу, переносом или
согласованным резервным копированием. Освобождаемые ресурсы зависят от движка:

| движок | что освобождается |
| --- | --- |
| SQLite | Хендл базы, после чего становятся доступны заблокированные им файловые операции. |
| redb | Исключительное открытие: другой store может открыть тот же путь. |
| JSON, TOML, RON | Фоновая работа; между сбросами постоянного файлового хендла нет. |

**Используйте текстовый store одним процессом за раз.** Независимые экземпляры
могут объединить разные правки данных, но при конфликте значений побеждает
последнее сохранение. Метаданные заменяются целиком, не объединяются;
конкурентные миграции также используют одни файлы восстановления.
Это не протокол координации нескольких процессов.

**Глобальное завершение устроено так же.** Удаление guard закрывает store
и логирует ошибки. `amethystate::shutdown()` до удаления guard возвращает
результат закрытия. Статическое хранилище само не удаляется: без guard
или явного shutdown можно потерять буфер даже при штатном выходе.

После ошибки `close` store всё равно закрыт. Для повторных попыток вызывайте
`save_now` **до** закрытия. Второй `close` не восстановит буфер.

Ожидание одной записи разобрано в
[Durability](/amethystate/ru/concepts/durability/).
