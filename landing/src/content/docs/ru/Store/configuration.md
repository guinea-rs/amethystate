Настраивайте store до открытия. Общие параметры задаются на `StoreBuilder`,
специфичные для движка — на `Redb`, `Text` или соответствующей конфигурации,
переданной в `backend`. Это не позволяет передать движку неподдерживаемую настройку.

Для обычного случая достаточно defaults. Ниже описано, когда их стоит менять.

## Тайминги

<!-- shown: how long a write waits, and how long an outside edit settles -->
```rust
let store = StoreBuilder::new(settings)
    .disk(|d| {
        d.debounce(Duration::from_millis(500))
            .watch_every(Duration::from_secs(2))
    })
    .build()?;
```
<!-- /shown -->

`StoreBuilder::disk` передаёт настройки диска с defaults: менять нужно только
нужные параметры.

`Disk::debounce` — интервал от первой накопленной записи до сброса. Последующие
записи добавляются в пачку, но не перезапускают таймер. Поэтому даже непрерывный
поток регулярно сохраняется. Больший интервал укрупняет пачки, меньший сокращает
объём изменений, которые можно потерять при аварии. Чтение в обоих случаях
сразу видит записи в буфере.

Плановый сброс фиксирует весь буфер. Durable-запись запрашивает сброс своего
пути: redb и SQLite фиксируют путь с потомками, а текстовый движок переписывает
документ и сохраняет все накопленные записи. См.
[Durability](/amethystate/ru/concepts/durability/).

`Disk::watch_every` задаёт перезагрузку внешних правок текстовых файлов.
Это пауза после последнего файлового события, не период опроса. Она объединяет
серию событий от редактора в одно перечитывание. Наблюдение использует
файловые уведомления платформы.

## Сброс, который продолжает падать

После ошибки изменения остаются в буфере. Store повторяет попытки до успеха
или своего удаления. Поэтому освобождение временно заполненного диска
позволяет продолжить сохранение без перезапуска приложения.

Настройте частоту попыток и момент уведомления приложения:

<!-- shown: how long a failing flush stays quiet -->
```rust
let store = StoreBuilder::new(settings)
    .disk(|d| {
        d.retry_every(Duration::from_secs(2))
            .give_up_after(Duration::from_secs(30))
    })
    .build()?;
```
<!-- /shown -->

`Disk::retry_every` задаёт интервал попыток. `Disk::give_up_after` — время,
после которого ошибка записывается в лог и передаётся наблюдателям.
Несмотря на название, этот параметр **не прекращает** повторные попытки.

Обычная запись в буфер не возвращает ошибку диска. Обрабатывайте сбои сохранения
централизованно через наблюдатель. Если результат нужен вызывающему коду,
используйте `durable()`, `save_now` или ожидаемый сброс.

### Как об этом узнать

К открытому store можно подключить наблюдатели для индикатора, телеметрии или теста:

<!-- shown: watching a store's saving from anywhere -->
```rust
let watch = store.on_persist_failure(|event| match event {
    PersistEvent::GaveUp { failure } => match failure.why.current_context() {
        StorageError::Flush => eprintln!("the disk is not taking writes: {:#}", failure.why),
        _ => eprintln!("not saved: {:#}", failure.why),
    },
    PersistEvent::Recovered => eprintln!("saved again"),
    _ => {}
});

if let Some(why) = store.persist_failure() {
    eprintln!("the last save that gave up: {why:#}");
}
```
<!-- /shown -->

Наблюдатель получает ошибку после `give_up_after`, а после успешного сохранения —
уведомление о восстановлении. Храните watch, пока нужна подписка. Колбэк работает
на потоке дебаунсера: закрывать оттуда store нельзя. Паника колбэка записывается
в лог и не останавливает дальнейшие сохранения.

`failure.why.current_context()` определяет категорию:

- `StorageError::Flush`: ошибка операции хранения, например заполненный,
  read-only или временно недоступный диск.
- `StorageError::Codec`: не удалось закодировать весь документ. Повтор той же
  операции с неизменёнными данными вряд ли поможет.

`failure.unsaved` перечисляет накопленные пути, но не обязательно путь-причину:
ошибка кодирования документа может не указывать отдельное значение.

Наблюдатель получает `Report<StorageError>` с контекстом движка.
`Store::persist_failure` позволяет запросить последнюю сообщённую ошибку;
после успешного сохранения она сбрасывается.

Большинство неподдерживаемых значений отклоняется ещё при записи, до буфера.
Наблюдатели описывают ошибки самого сохранения.

## Одна запись в один файл

У текстовых движков есть дополнительные повторы **внутри** одной попытки
сброса. Общая политика повторов применяется после исчерпания этих попыток:

<!-- shown: how hard one write to one file fights -->
```rust
let store = StoreBuilder::new(settings)
    .backend(Text::json().file_write(|w| {
        w.writing(WriteAttempts::times(3).apart(Duration::from_millis(50)))
            .replacing(WriteAttempts::times(20).apart(Duration::from_millis(250)))
    }))
    .build()?;
```
<!-- /shown -->

Текстовый движок сначала пишет временный документ, затем заменяет целевой файл.
`writing` и `replacing` задают разные бюджеты для этих этапов. Заполненный диск
обычно не освобождается за миллисекунды, а файл, занятый антивирусом или
синхронизатором, может вскоре освободиться. Поэтому бюджет замены по умолчанию дольше.

redb и SQLite работают через хендлы базы, а не этот протокол замены файла.
Данные настройки к ним не относятся.

## Чего store не примет

`limits` ограничивает глубину и переносимость значений. См.
[Ограничения store](/amethystate/ru/store/limits/).

## Чтение большой коллекции

<!-- shown: letting a large read use more than one core -->
```rust
let store = StoreBuilder::new(settings)
    .backend(Redb::new().parallel_reads(true))
    .build()?;
```
<!-- /shown -->

Параллельное декодирование может ускорить открытие больших коллекций.
Оно использует лениво создаваемый пул потоков и по умолчанию выключено:
приложение само решает, нужен ли дополнительный пул. Маленькие коллекции
читаются в вызывающем потоке, без расходов на распределение работы.

Настройка доступна для redb и движка в памяти. SQLite и текстовые движки
декодируют данные в вызывающем потоке.

## Кеш redb

<!-- shown: giving redb a cache of its own -->
```rust
let store = StoreBuilder::new(settings)
    .backend(Redb::new().cache_size(64 << 20))
    .build()?;
```
<!-- /shown -->

Собственный кэш redb по умолчанию отключён. Поля, ячейки и карты уже хранят
живое состояние в памяти, и второй кэш может дублировать данные.
Прямое чтение из store без него использует файловый кэш операционной системы.

Если преобладают чтения через `Kv` или сканирование, кэш redb может помочь.
Его размер задаётся в байтах; эффект стоит измерить на данных приложения.
Кэш меняет скорость чтения, но не гарантии коммита.

## Что настройкой не считается

Билдер также принимает входные данные приложения:

- `migrations`: шаги миграции;
- `provide`: зависимости для этих шагов;
- `context`: зависимости для правил и собственного открытия структур.

Зависимости миграции могут быть не-`Send`, например `Rc`: шаги выполняются
синхронно внутри `migrate` в вызывающем потоке. Правила могут вызываться
и наблюдателем файлов, поэтому значения `context` должны быть `Send + Sync`.
См. [Миграции](/amethystate/ru/migrations/overview/) и
[Правила](/amethystate/ru/state/rules/).
