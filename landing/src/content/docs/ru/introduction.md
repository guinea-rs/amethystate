Я не верю в GUI на Rust. Тем, кто хочет писать интерфейс, а не изобретать
велосипед, скажу: берите Tauri или Electron.

Сам я начинал с вопроса «на чём писать GUI?» и, недолго думая, дошёл до Slint.
Если нужно только нарисовать интерфейс, Rust — выбор ещё терпимый. Но эту
потребность перерастаешь быстро, а за ней встаёт россыпь задач не менее важных:
где хранить состояние, как обновляться, и ещё десяток мелочей. В Tauri они
решены, а на нативном десктопе не решены вовсе.

Эта библиотека — мой ответ, один из десятка возможных, на вопрос «как сохранить
ширину сайдбара между запусками?». Я читал исходники Halloy, Sniffnet и проектов
помельче. Каждый решает этот вопрос на месте, под свои нужды, и, на мой взгляд,
кривовато. Я решил поднапрячься — то есть поднапрячь видеокарты на серверах
Anthropic — и решить задачу чуть системнее.

## Что это

`amethystate` сохраняет состояние приложения между запусками и уведомляет код
об изменениях. Вы объявляете состояние обычными структурами Rust, а библиотека
предоставляет хендлы полей, хранение и миграции.

**Store** управляет сохранёнными данными, буфером записей и подписками.
Откройте его при запуске приложения и создайте на его основе структуры состояния.

```rust
#[amethystate(prefix = "network")]
pub struct NetworkState {
    #[amestate(default = "127.0.0.1".to_string())]
    pub host: String,

    #[amestate(default = 8080u16)]
    pub port: u16,
}
```

После `state.port().set(9090)` чтение возвращает `9090`, а подписчики `port`
уже получили уведомление. Сохранение на диск происходит отдельно.

Подписку можно ограничить полем, ключом карты или путём. Компонент интерфейса,
который следит за `port`, не получает изменений `host` и может обновляться
только при изменении нужного ему значения.

## Что решает за вас

**Расположение и формат файла.** Store можно открыть по имени в системном
каталоге данных приложения или указать путь вручную. **Движок** определяет
формат хранения: redb, SQLite или текстовый документ.

**Когда сохранять.** Файловые движки сначала записывают изменения в буфер,
а затем сбрасывают его на диск через заданный интервал после первой записи.
Перетаскивание ползунка поэтому не требует записи на диск на каждом кадре.
Вызовите `save_now`, чтобы дождаться сохранения всех накопленных изменений.
Закрытие store тоже сбрасывает буфер.

**Как кодировать значения.** redb хранит значения в MessagePack, SQLite —
в JSON, а текстовые движки используют JSON, TOML или RON напрямую. Одно
объявление состояния можно использовать с разными движками, но набор
допустимых значений зависит от формата. Неподдерживаемое значение вызовет ошибку.

**Как нормализовать значения.** `rule` на поле обрабатывает значения,
прочитанные из хранилища или записанные вашим кодом: например, ограничивает
размер окна или заменяет недоступную тему. Исправления записываются обратно
в store. Проверки, которым нужны несколько полей, выполняют в собственном `Open`.

**Как обновить схему.** Store хранит схему каждой структуры. Если поднять
версию и открыть store через `migrate`, библиотека выполнит ваши шаги миграции.
Изменение схемы без новой версии попадёт в отчёт о дрейфе с диффом,
но не заблокирует запуск.

**Как обработать внешнюю правку.** Текстовые движки следят за своими файлами
и уведомляют подписчиков, когда другая программа меняет значение. При сохранении
они добавляют накопленные записи в текущий документ, а не заменяют его старой копией.

## Два вида состояния

Выберите, нужны ли приложению реактивные хендлы или обычные значения.
Хранение, схемы и миграции в обоих режимах одинаковые.

- **Реактивное**, по умолчанию: чтение, запись и подписки через хендлы полей.
  Этот режим используется в большинстве примеров книги.
- **Persistent-only**: загрузка обычных полей структуры и явное сохранение.
  Подходит, когда приложение само управляет обновлениями и подписки не нужны.
  Загруженная структура не получает изменений, сделанных в другом месте.

## Для чего это и для чего нет

Библиотека подходит для раскладки окон, открытых панелей, фильтров, списков
недавних файлов и кэшей между запусками. API рассчитано и на небольшие структуры
настроек, и на коллекции с тысячами ключей.

Это не универсальная база данных: здесь нет языка запросов, индексов и публичного
API транзакций. Доступ к данным идёт по путям. Можно открыть несколько store,
но возможность открыть один файл повторно зависит от движка — см.
[Открытие store](/amethystate/ru/store/opening/).
